# 特种设备全生命周期 Demo 需求规格

> 2026-10-28｜第一阶段审核稿。仅需求、源码分析和设计；下述新增功能均为规划，不代表已经实现。源码事实见 [current-state.md](current-state.md)。

## 1. 项目背景和边界

产品：检验检测院一体化服务平台；模块：特种设备全生命周期管理；交付：可操作、可展示、可解释的 Web Demo。基于 D:\Projects\OpenCMMS 二次开发，保留 Django、DRF、SQLite、原生 HTML/CSS/JavaScript 和现有 UI。产品部已认可页面风格，沿用工作台、设备台账、工单管理、保养计划、点检记录、备件管理、报表统计七个菜单，不按角色复制前端。

第一阶段只交付本目录五份 Markdown；不修改业务源码、数据库、依赖，不迁移、不重置、不提交。当前已有 93 台设备、2 张工单、3 个保养计划等记录，必须保留，真实性尚未核实，不可当作虚构演示数据发布。

需求依据是用户提供的生命周期思维导图文字摘要，未收到原始 XMind 文件。以下映射不声称核对过原图的其他分支。

| 4 报修、问题、维修进场和记录 | 点检异常上报、工单 CM、进场/处理记录 | P0 | 使用单位报修→分配→接单→进场→完工→反馈确认 |
| 5 自然报废、拆除、解体等处置 | 档案“停用与报废” | P1 | 原因、申请、单级审批、拆除/解体/其他处置均留档 |

| 7 维修单位接维修任务 | 工单管理 CM 筛选和任务动作 | P0 基础/P1 完整角色 | 接单、过程、反馈可操作且不能跨单位越权 |
| 8 检测单位任务、过程、结果 | 工单管理“检测”页签，档案“检测与检验” | P1 | 检测与检验概念、任务类型、结果记录分开 |

| 10 从建档到停用报废的历史 | 档案“生命周期”页签 | P0 核心/P1 扩展 | 事件按业务时间排列、可回看来源和操作者 |

安装测试属于安装业务，不能用日常点检替代；日常点检不得标为法定检验；维修完成、业务验收和设备重新投入使用是不同动作。

## 3. 用户角色

| 业务身份 | 范围与主要操作 |
| --- | --- |
| 平台管理员 | 管理虚构单位、账号、授权、演示数据；跨单位访问须审计 |
| 使用单位负责人/主管 | 本单位设备建档、计划、指派受托单位、工单关闭、模拟验收、停用/报废申请及获授权审批 |
| 使用单位操作人员/点检员 | 本单位授权设备点检、问题上报、查看历史；不得批准复用或报废 |
| 维护单位负责人/维护人员 | 接收本单位受托 PM 任务、分配执行人、过程记录和完工反馈 |
| 维修单位负责人/维修人员 | 接收本单位受托 CM 任务、接单、进场、维修、完工反馈 |
| 检测单位负责人/检测人员 | 本单位检测任务、过程、结果提交；无权替检验单位出结论 |
| 检验单位负责人/检验人员 | 本单位检验任务、结果提交；模拟结果须标识，不产生真实法定证明 |
| 报废审批人 | 使用单位指定主管；默认不得审批自己提交的申请 |

现有 admin/supervisor/engineer/technician/operator 保留作兼容字段，不能据此推断新业务身份。角色通过“单位成员关系+能力”落地，单位可同时具有维护与维修等能力。前端按钮和服务端授权同时控制，后端为最终依据。

## 4. 页面功能与验收标准

| ID | 页面/功能 | 验收标准 |
| --- | --- | --- |
| A1 | 设备台账 | 保留原列表和操作风格；新增类别、使用单位、负责人、最近/下次检验日期；编号、名称、型号、规格、位置均可检索或在详情查看 |
| A2 | 设备档案 | 展示资产原字段、安装单位/位置、登记编号/登记日期/登记状态、运行状态、检验提示；旧设备新增字段空值可正常显示 |
| B1 | 点检计划/项目 | 设备、模板版本快照、执行人、日常频次/指定日期可保存；生成具体任务避免用记录数充当计划数 |
| B2 | 点检执行 | 填实际执行时间、逐项正常/异常、读数/备注；必检项漏填拒绝提交；执行者从登录用户取值 |
| B3 | 异常和历史 | 异常可上报关联唯一 CM 工单，刷新或重复提交不重复建单；查看来源点检、执行人、执行时间 |
| C1 | 工单管理 | 使用单位创建 PM/CM→指派单位/人→受托方接单→开始/进场→记录过程→完成→使用单位确认关闭；非法跳转拒绝 |
| C2 | 保养/备件兼容 | 原计划编辑、启停、手动生成工单保留；设备/工单/备件原操作经隔离环境回归，发现的现有缺陷先修复 |
| D1 | 检测与检验 | 分开任务、单位、过程、结果；不适用项目可说明原因，不能自动判合格；受托人员仅修改本单位任务 |
| D2 | 验收与复用 | 验收必须关联最终结果；不通过、资料缺失、规则未知、未关闭的阻断问题不能一键恢复运行 |
| E1 | 停用报废 | 停用原因必填；申请→审核→通过/驳回→处置登记，保留原始记录；报废后不能普通编辑改回运行 |
| F1 | 生命周期 | 建档、安装、维护、维修、点检、检测、检验、状态变更、报废形成统一时间线；事件有时间、单位、人员、来源、摘要 |
| G1 | 报表 | 设备总量/类别/状态、CM 待修/完工、点检完成率/异常、检验临期/到期/结果均由后端真实聚合返回 |
| G2 | 图表与筛选 | 日期、类别、单位筛选影响所有相关指标；清楚标出统计口径、空值/无计划状态；图表有对应数值与明细入口 |
| U1 | UI 与响应式 | 七菜单、深色侧栏、蓝色主色、SVG 图标、卡片/表格/模态框沿用；1366/1920 桌面、768 平板、390 手机验证导航和操作可达 |
| S1 | 权限 | 匿名请求拒绝；单位 A 无法通过列表、详情、外键、报表、导入导出或动作访问单位 B 的未授权数据 |
| S2 | 演示标识 | 所有新增样本为虚构；检测/检验结论、证书/许可状态均显示“模拟业务数据，不构成法定检验证明或许可” |

## 5. 优先级与交付范围

P0：修复影响演示的已有缺陷、单位隔离最小基础、台账增强、日常点检完整操作、基础维护维修流转、生命周期核心事件、报表页面。检验日期人工录入示例且注明来源，不假装已完成 P1 检验流程。

P1：单位角色完整管理，安装测试及使用登记资料、检测与检验全过程、验收及复用条件、停用报废及处置、时间线和报表接入上述事件。单级报废审批属于 P1。

P2：多级/可配置审批、附件证书管理和访问权限、导出及高级/定时报表、更丰富的异常分级、转派、复检和处置策略。原有设备/工单导入导出基础能力的修复属于 P0，不延期到 P2。

## 6. 验收与人工决策

不为不同类别设备虚构统一检验周期。不在本稿给出法定周期或法律适用判断；类别、规范来源/版本、生效范围、下次日期、复用条件待业务专家确认。规则未知时提示“待业务确认”，不得推定可用；演示可使用明确标记的虚构日期。

需审核：首批设备类别及细分范围、使用单位对外委单位的数据授权范围、审批人与申请人是否分离、P0 是否接受最小单位配置而完整管理放 P1、现有 93 台设备归属与真实性、演示账户与数据对外展示范围。推荐默认值见设计，尚未获得用户批准。

验收以隔离测试库的 API/权限/迁移回归和真实浏览器操作为准；现有单元测试文件存在不等于测试已经通过。
